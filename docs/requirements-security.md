# Специфікація вимог безпеки (фаза аналізу вимог)

Проєкт: **SDLC Security Demo (Flask)** · Модель розробки: **DevSecOps** (GitHub Flow + CI-гейти безпеки)
Автор: Кондратюк Т. С., гр. 22340 · Версія специфікації: 1.1

## 1. Область застосунку та активи

Flask-вебдодаток із чотирма маршрутами: `/` (головна), `/search` (пошук постів), `/echo` (відображення
повідомлення), `/login` + `/profile` (автентифікація і профіль). Дані зберігаються в SQLite.

| ID | Актив | Властивість (CIA) | Цінність |
|----|-------|-------------------|----------|
| A1 | Облікові дані користувачів (таблиця `users`) | C, I | Висока |
| A2 | Сесійний cookie (`session`, підписаний `SECRET_KEY`) | C, I | Висока |
| A3 | `SECRET_KEY` та інші секрети конфігурації | C | Критична |
| A4 | Контент (таблиця `posts`) | I, A | Середня |
| A5 | Журнали аудиту автентифікації | I, A | Середня |
| A6 | Доступність сервісу (HTTP 5000) | A | Середня |

Ролі: **anonymous** (головна, пошук, echo, форма входу), **user** (власний профіль).

## 2. Функціональні вимоги безпеки

| ID | Вимога | Критерій приймання | ASVS 4.0.3 | Загрози |
|----|--------|--------------------|------------|---------|
| AUTH-1 | `/profile` доступний лише автентифікованому користувачу | без сесії → 302 на `/login` | V4.1.1 | T-EoP-1 |
| AUTH-2 | Блокування після 5 невдалих спроб входу на 15 хв (per username + IP) | 6-та спроба → 429 | V2.2.1 | T-S-1 |
| AUTH-3 | Однакове повідомлення для неіснуючого логіна та хибного пароля | текст «Invalid credentials» в обох випадках | V2.2.x / V3 | T-I-3 |
| AUTH-4 | Регенерація сесії після входу, вихід (`/logout`) очищає сесію | `session.clear()` перед записом `user_id` | V3.2.1, V3.3.1 | T-S-2 |
| STOR-1 | Паролі зберігаються лише як сольований стійкий хеш (scrypt / PBKDF2 ≥ 600 000) | у БД немає відкритих паролів | V2.4.1 | T-I-2 |
| INP-1 | Усі SQL-запити параметризовані | Bandit B608 / Semgrep tainted-sql = 0 | V5.3.4 | T-T-1 |

| INP-3 | Обмеження довжини вхідних параметрів (`q`, `msg` ≤ 200 символів) | довший параметр → 400 | V5.1.3 | T-D-1 |
| CSRF-1 | Форми, що змінюють стан, захищені CSRF-токеном | POST без токена → 400 | V4.2.2 | T-T-2 |
| SESS-1 | Cookie сесії: `HttpOnly`, `SameSite=Lax`, `Secure` у production | заголовок Set-Cookie містить прапорці | V3.4.1–V3.4.3 | T-S-2 |
| HDR-1 | Заголовки безпеки: CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy | ZAP baseline без попереджень про заголовки | V14.4 | T-I-1 |
| LOG-1 | Аудитна подія для кожного входу / невдалої спроби / блокування (JSON, без паролів) | запис у `logs/audit.log` | V7.1.1, V7.2.1 | T-R-1 |
| ERR-1 | Debug-режим вимкнений; помилки без стек-трейсів | Bandit B201 = 0 | V7.4.1, V14.3.2 | T-EoP-2 |
| CONF-1 | Секрети лише у змінних оточення / GitHub Secrets; без значень за замовчуванням у коді | застосунок не стартує без `SECRET_KEY` | V2.10.4, V14.1 | T-I-4 |
| DEP-1 | Залежності закріплені, без відомих вразливостей | pip-audit = 0 | V14.2.1 | T-T-3 |

## 3. Нефункціональні вимоги безпеки

| ID | Вимога |
|----|--------|
| NFR-1 | **Відповідність стандартам:** OWASP ASVS 4.0.3 рівень L1 (обов'язково) + вибрані пункти L2; OWASP Top 10 2021; NIST SSDF (SP 800-218) як рамка процесу; ДСТУ ISO/IEC 27001 (A.8.25–A.8.29 «Безпечна розробка»). |
| NFR-2 | **Автоматизація:** SAST (Semgrep, Bandit), SCA (pip-audit) і тести безпеки запускаються на кожен push / PR; DAST (OWASP ZAP baseline) — на кожен push у `main` і вручну. |
| NFR-3 | **Гейт якості:** злиття в `main` лише через PR, з успішним `security-gate` (0 High/Critical від Bandit/Semgrep/pip-audit) і переглядом Security Champion. |
| NFR-4 | **Час реакції (SLA) на вразливості:** Critical — 24 год, High — 3 дні, Medium — 14 днів, Low — у наступному релізі. |
| NFR-5 | **Збереження даних:** БД SQLite у томі `/data`, доступ лише користувачу контейнера; журнали аудиту зберігаються ≥ 90 днів; персональні дані — лише логін. |
| NFR-6 | **Продуктивність під час DAST:** baseline-сканування пасивне, тривалість ≤ 10 хв, не впливає на інші середовища. |
| NFR-7 | **Експлуатаційність:** документовані процедури тріажу SAST/DAST, шаблони Issue і PR, журнал змін. |
| NFR-8 | **Контейнер:** образ на `python:3.11-slim`, запуск від непривілейованого користувача. |

## 4. Потенційні загрози (огляд, деталі — `threat-model.md`)

- **T-T-1** SQL-ін'єкція в `/search` (параметр `q` в f-string).
- **T-I-1** Відбитий XSS у `/echo` (параметр `msg` повертається як HTML).
- **T-S-1** Перебір паролів (немає rate limiting), **T-I-2** відкриті паролі в БД.
- **T-S-2** Викрадення / фіксація сесії (cookie без прапорців, немає регенерації).
- **T-I-4** Витік / підробка сесії через жорстко заданий `SECRET_KEY`.
- **T-EoP-2** RCE через Werkzeug debugger (`debug=True`).
- **T-R-1** Заперечення дій через відсутність аудиту.
- **T-D-1** DoS через важкі `LIKE`-запити з довгими параметрами.
- **T-T-3** Вразливі залежності (ланцюг постачання).

## 5. Базові цілі безпеки

| Ціль | Формулювання | Як вимірюється |
|------|--------------|----------------|
| Конфіденційність (C) | Облікові дані, сесії та секрети недоступні неавторизованим особам | STOR-1, SESS-1, CONF-1 виконані; 0 High у SAST |
| Цілісність (I) | Дані в БД змінюються лише легітимними запитами застосунку | INP-1, CSRF-1; 0 SQLi у SAST/DAST |
| Доступність (A) | Сервіс доступний під час нормальної роботи і тестування | INP-3, AUTH-2; DAST без збоїв |
| Підзвітність | Кожна спроба автентифікації фіксується | LOG-1 |
| Відповідність | ASVS L1 виконано повністю | чекліст в `audit-report.md` |
